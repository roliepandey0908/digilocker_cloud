# DigiLocker Backend: Data Model and API Contract (Draft)

**Status:** first implementation contract; AWS independent  
**Audience:** backend and dashboard teammates  
**Base path:** `/api/v1`  
**Identity:** during local development, use a clearly marked mock identity; later map the verified Cognito JWT `sub` and groups/roles to this contract.

This document defines the shared backend used by the Issuer, Citizen, and Requester dashboards. It does not assume that any AWS resource, table, bucket, or Cognito pool already exists.

## 1. Design rules

- The backend is the single source of authorization decisions. Hiding a button in a dashboard is not security.
- Use stable opaque IDs in APIs. Do not use enrollment numbers, email addresses, or document URIs as authorization proof.
- Keep PDF bytes in a storage adapter. Metadata and access decisions belong in the application data store.
- A requester can read a document only after the citizen approves a request for that specific document and the grant is still valid.
- Record consent and important state changes as append-only audit events.
- Never return storage object keys, credentials, or internal implementation details in API responses.
- Do not put real credentials or personal data in examples, source control, or test fixtures.

## 2. Core model

IDs below are opaque strings generated by the backend (UUIDs are suitable). Timestamps are ISO-8601 UTC.

### User

Represents an authenticated application identity.

| Field | Meaning |
| --- | --- |
| `id` | Backend user ID; later linked to Cognito `sub` |
| `role` | `ISSUER`, `CITIZEN`, `REQUESTER`, or `ADMIN` |
| `displayName` | Name shown in the dashboard |
| `email` | Optional contact; do not use as the primary key |
| `status` | `ACTIVE` or `DISABLED` |
| `createdAt`, `updatedAt` | Audit timestamps |

A user has one active role in the first version. If a person needs multiple roles later, evolve this to a role collection deliberately.

### IssuerOrganization

Represents an approved university or institution.

| Field | Meaning |
| --- | --- |
| `id` | Opaque issuer organization ID |
| `name` | Institution name |
| `status` | `PENDING`, `ACTIVE`, or `DISABLED` |
| `createdAt`, `updatedAt` | Audit timestamps |

An issuer user is linked to an organization by a separate membership mapping. Only active issuer users may issue records for their own organization.

### CitizenProfile

Represents a citizen/student profile owned by a CITIZEN identity.

| Field | Meaning |
| --- | --- |
| `id` | Opaque citizen ID |
| `userId` | Owning User ID |
| `enrollmentId` | Institution-scoped student identifier; sensitive, never use as public lookup |
| `issuerOrganizationId` | Institution that verified/registered the profile |
| `status` | `PENDING`, `ACTIVE`, or `DISABLED` |
| `createdAt`, `updatedAt` | Audit timestamps |

The pair `issuerOrganizationId + enrollmentId` must be unique. Do not expose enrollment IDs in requester APIs.

### Document

Represents an issued document and its metadata. The PDF itself is held behind a `DocumentStorage` interface.

| Field | Meaning |
| --- | --- |
| `id` | Opaque backend document ID |
| `documentUri` | Unique, unguessable public reference; not an access token |
| `citizenId` | Owning citizen |
| `issuerOrganizationId` | Issuing institution |
| `issuedByUserId` | Authenticated issuer user |
| `documentType` | e.g. `MARKSHEET`, `DEGREE_CERTIFICATE` |
| `title` | Human-readable label |
| `fileName`, `mediaType`, `sizeBytes` | Validated file metadata |
| `sha256` | Lowercase 64-character hex digest of the uploaded bytes |
| `storageRef` | Private adapter reference; internal only, never returned |
| `status` | `ACTIVE` or `REVOKED` |
| `issuedAt`, `createdAt`, `updatedAt` | Timestamps |

The issuing organization must match the citizen profile's registered organization unless an explicit cross-institution policy is approved. A document URI locates a record; it does not grant access.

### VerificationRequest

Represents a request by a requester to verify specific citizen documents.

| Field | Meaning |
| --- | --- |
| `id` | Opaque request ID |
| `requesterUserId` | Requesting organization/user |
| `citizenId` | Target citizen; visible only to authorized participants |
| `purpose` | Short, user-visible reason for requesting verification |
| `documentIds` | Exact requested documents; at least one |
| `status` | `PENDING`, `APPROVED`, `REJECTED`, `EXPIRED`, or `REVOKED` |
| `expiresAt` | Consent deadline / grant expiry |
| `decidedAt` | Citizen decision timestamp, if decided |
| `createdAt`, `updatedAt` | Audit timestamps |

Approval applies only to the listed documents and expires at `expiresAt`. Rejection does not reveal document content. Citizens may revoke an approved request; the backend must deny subsequent reads.

### AuditEvent

Append-only record for security-relevant events.

| Field | Meaning |
| --- | --- |
| `id` | Opaque event ID |
| `actorUserId` | User who caused the event |
| `action` | E.g. `DOCUMENT_ISSUED`, `CONSENT_APPROVED`, `DOCUMENT_VIEWED` |
| `resourceType`, `resourceId` | Affected resource |
| `occurredAt` | UTC timestamp |
| `details` | Minimal non-secret context; avoid copying document contents or tokens |

## 3. Relationships

- User (CITIZEN) 1 — 1 CitizenProfile in the initial version.
- IssuerOrganization 1 — many issuer memberships and citizen profiles.
- CitizenProfile 1 — many Documents.
- Requester User 1 — many VerificationRequests.
- VerificationRequest references one citizen and one or more exact Documents.
- AuditEvents reference the acting user and affected resource.

## 4. API conventions

- JSON request and response bodies use camelCase.
- IDs and timestamps are generated by the backend unless explicitly stated.
- Authenticated identity and role come from the security context, never from a client-supplied `userId` or `role`.
- List endpoints return `items` and may later add cursor pagination.
- Return a consistent error body:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "One or more fields are invalid.",
  "requestId": "req_example"
}
```

- Common status codes: `200` read/update, `201` create, `204` successful delete/revoke with no body, `400` invalid input, `401` unauthenticated, `403` wrong role or ownership, `404` missing resource, `409` conflicting state, `413` file too large, `415` unsupported file type, `500` unexpected server error.
- Do not distinguish “citizen does not exist” from “not allowed to see this citizen” in requester-facing lookup responses if that would expose enrollment data.

## 5. Endpoint contract

### Issuer flow

#### Register a citizen profile

`POST /api/v1/issuer/citizens` — role `ISSUER`

```json
{
  "enrollmentId": "STUDENT-2026-001",
  "displayName": "Asha Example",
  "citizenUserId": "usr_opaque_citizen"
}
```

Returns `201` with the created citizen `id`, `status`, and issuer organization ID. The issuer organization and acting user come from the authenticated identity, not the body. In a later onboarding design, replace `citizenUserId` with a controlled invitation/link process.

#### Issue a document

`POST /api/v1/issuer/documents` — role `ISSUER`, multipart form

Parts:
- `metadata`: JSON with `citizenId`, `documentType`, and `title`
- `file`: one PDF (initial limit 10 MB; validate actual content, not only filename)

Returns `201`:

```json
{
  "id": "doc_opaque_123",
  "documentUri": "urn:digilocker:document:opaque-random-value",
  "citizenId": "cit_opaque_123",
  "issuerOrganizationId": "org_opaque_123",
  "documentType": "MARKSHEET",
  "title": "Semester 1 marksheet",
  "fileName": "semester-1.pdf",
  "mediaType": "application/pdf",
  "sizeBytes": 245760,
  "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "status": "ACTIVE",
  "issuedAt": "2026-11-09T12:00:00Z"
}
```

The response omits the private storage reference. The service calculates SHA-256 from received bytes; it does not trust a client-provided hash.

#### List issuer documents

`GET /api/v1/issuer/documents?citizenId=...` — role `ISSUER`

Returns only documents issued by the caller's organization. Cross-organization access is forbidden.

### Citizen flow

#### List my documents

`GET /api/v1/citizen/documents` — role `CITIZEN`

The citizen profile is derived from the authenticated identity.

```json
{
  "items": [
    {
      "id": "doc_opaque_123",
      "documentUri": "urn:digilocker:document:opaque-random-value",
      "issuerName": "Example University",
      "documentType": "MARKSHEET",
      "title": "Semester 1 marksheet",
      "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
      "status": "ACTIVE",
      "issuedAt": "2026-11-09T12:00:00Z"
    }
  ]
}
```

#### List consent requests

`GET /api/v1/citizen/verification-requests?status=PENDING` — role `CITIZEN`

Returns requests targeting the authenticated citizen, including requester display name, purpose, requested document labels, expiry, and status. It must not return private PDF data.

#### Decide consent

`POST /api/v1/citizen/verification-requests/{requestId}/decision` — role `CITIZEN`

```json
{
  "decision": "APPROVE"
}
```

Allowed decisions: `APPROVE` or `REJECT`. A request may be decided only by its target citizen and only while pending and unexpired. Returns the updated request. Repeating the same decision may return the existing state; a conflicting second decision returns `409`.

#### Revoke consent

`POST /api/v1/citizen/verification-requests/{requestId}/revoke` — role `CITIZEN`

Only the target citizen may revoke an approved, unexpired request. Returns updated status `REVOKED`.

### Requester flow

#### Create a verification request

`POST /api/v1/requester/verification-requests` — role `REQUESTER`

```json
{
  "citizenId": "cit_opaque_123",
  "documentIds": ["doc_opaque_123"],
  "purpose": "Verify degree for employment application",
  "expiresAt": "2026-11-16T12:00:00Z"
}
```

Returns `201` with status `PENDING`. The server checks that every document belongs to the specified citizen and is active. The expiry must be in the future and within a configured maximum window. Creating a request does not grant access.

#### Check request status

`GET /api/v1/requester/verification-requests/{requestId}` — role `REQUESTER`

Only the requester who created it may read the request. Returns status, purpose, selected document summaries, decision time, and expiry.

#### Read an approved document

`GET /api/v1/requester/verification-requests/{requestId}/documents/{documentId}/content` — role `REQUESTER`

The server verifies requester ownership, approved and unexpired consent, document membership in the request, and active document status on every read. Return PDF bytes with `Content-Type: application/pdf` and a safe `Content-Disposition`. Record a `DOCUMENT_VIEWED` audit event. A temporary signed URL may be considered later, but it must be short-lived and issued only after these checks.

## 6. Role and ownership matrix

| Operation | ISSUER | CITIZEN | REQUESTER | ADMIN |
| --- | --- | --- | --- | --- |
| Register citizens / issue documents | Own organization only | — | — | Administrative policy only |
| List own citizen documents | Own organization only | Own profile only | — | Administrative policy only |
| View incoming consent requests | — | Own profile only | — | Administrative policy only |
| Approve/reject/revoke consent | — | Own profile only | — | No impersonation by default |
| Create verification request | — | — | Own identity only | Administrative policy only |
| Read approved document content | — | Own documents | Request creator with active grant | No content access by default |

ADMIN is reserved for operational/user-management endpoints to be specified separately; it does not automatically bypass document consent.

## 7. First local implementation slice

Implement these in order, without AWS:
1. Java records/DTOs and enums matching this contract.
2. Service-level ownership and state-transition rules.
3. Local in-memory repositories and a local PDF storage adapter.
4. Issuer issue-document endpoint and citizen list-documents endpoint.
5. Requester request + citizen decision + requester authorized content read.
6. Unit and API tests for role/ownership checks, expiry, revocation, and invalid state changes.

When AWS is connected, replace adapter implementations with DynamoDB and private S3 implementations. Keep API routes and domain behavior unchanged.

## 8. Decisions to confirm with the team before freezing

- Does issuer registration link an existing citizen account, or create an invitation for the student to claim?
- Can one citizen have profiles from multiple institutions?
- Are requesters organizations with multiple user accounts, or individual users in the first release?
- What is the maximum PDF size and allowed document type list?
- How long may a consent grant remain valid?
- Should approval allow repeated reads until expiry, or only one read?
